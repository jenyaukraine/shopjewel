## 0. Общий контекст проекта (нужен для всех задач)

**Что это.** Магазин `6 Moments` на чистом OpenCart `4.1.0.3`. Весь наш код живёт
в одном расширении `opencart/noveraile` и накладывается поверх неизменённого ядра при каждом
релизе. Ядро не патчим никогда — только события (`oc_event`) и переопределение view-роутов.

**Инфраструктура.**
- `noveraile-store` (PHP/Apache) + `noveraile-db` (MySQL 8.4) в Docker, общий edge — Caddy.
- Деплой: любой push в `main` → [.github/workflows/deploy-production.yml](.github/workflows/deploy-production.yml).
  Перед заменой контейнеров делается дамп MySQL, бэкапы лежат в `$DEPLOY_PATH/backups` 14 дней.
- **База данных переживает релизы.** Это ключевой факт: половина правок ниже — это правки данных,
  а не кода, и они не «выкатятся» сами.
- Прод/дев-стенд: `katya-dev.duckdns.org`.

**Как устроен каталог.**
- Ассортимент — фид [opencart/noveraile/data/catalog-feed.json](opencart/noveraile/data/catalog-feed.json):
  **476 товаров, 6855 вариантов цены, 3653 изображения**.
- Собирается из CSV поставщика: [tools/build-catalog-feed.mjs](tools/build-catalog-feed.mjs).
- Импортируется в OpenCart: [opencart/noveraile/admin/model/module/catalog_feed.php](opencart/noveraile/admin/model/module/catalog_feed.php),
  CLI: `docker exec noveraile-store noveraile-import-catalog --status`.
- Модель данных: **1 товар = 1 артикул**. Все комбинации «проба × качество бриллианта» —
  это одна обязательная опция-select «Gold & diamond quality» с 15 значениями
  (3 пробы `375/585/750` × 5 качеств `LAB, G/SI, G/VS2, F/VS2, D/VVS2`).
  Цена товара = минимальная комбинация, каждое значение опции добавляет точную разницу.
- Для колец добавляется вторая обязательная опция «Ring size» со значениями EU `50,52,54,56,58,60`.
- Фасеты фильтра считаются из БД и кешируются: [opencart/noveraile/catalog/model/catalog.php](opencart/noveraile/catalog/model/catalog.php),
  ключи кеша `noveraile.facet.v3.*`, сбрасываются импортом.

## 0.1. Блокеры и системные находки (читать до начала работ)

### B1 — «Too many connections» на 6moments.store (P0) — **исправлено в этой ветке**

Симптом (наблюдался и на `6moments.store`, и на `katya-dev.duckdns.org`): на любой URL

```
Error: Could not make a database link using opencart@db!
Message: Too many connections
```

Ошибка **перемежающаяся** — сайт то падает, то отвечает нормально. Это классический признак
исчерпания пула соединений на пике, а не постоянной поломки конфигурации.

**Корневая причина — арифметика, а не баг.** Складываются три числа:

| Что | Значение | Откуда |
|---|---|---|
| Одновременных PHP-процессов | **до 150** | Debian-дефолт `mpm_prefork` в образе `php:8.3-apache` |
| Лимит соединений MySQL | **151** | дефолт `mysql:8.4`, в compose не переопределён |
| Память контейнера витрины | **768 МБ** | `mem_limit` в `docker-compose.yml` |

Каждый дочерний процесс Apache держит один запрос OpenCart **и одно соединение с MySQL** на всё
время запроса. То есть Apache по умолчанию имеет право занять ровно столько соединений, сколько
MySQL вообще может выдать — запаса нет ни одного. Дальше достаточно любого всплеска:

- обход поисковым/AI-ботом каталога из 429 товаров;
- холодный кеш фасетов сразу после деплоя (импорт сбрасывает `noveraile.facet.*`, и каждый
  следующий запрос пересчитывает фасеты — запросы становятся длиннее, процессы копятся);
- фоновая докачка изображений после релиза.

Плюс два усилителя:
- 150 процессов × ~45 МБ ≫ 768 МБ лимита контейнера — контейнер начинает свопить/ловить OOM
  раньше, чем упрётся в MySQL, запросы замедляются, конкурентность растёт дальше (спираль);
- `wait_timeout` MySQL по умолчанию **8 часов** — соединение, брошенное на середине запроса,
  остаётся занятым до конца дня.

**Что сделано в этой ветке:**

1. `docker/apache-tuning.conf` (новый) — потолок конкурентности приведён к тому, что контейнер
   реально может обслужить: `ServerLimit`/`MaxRequestWorkers` = **16**, `MaxConnectionsPerChild 500`,
   `KeepAliveTimeout 2`, `Timeout 60`. При переполнении запросы встают в очередь и ждут —
   это правильный режим отказа вместо «пятисоток» всему сайту.
2. `Dockerfile` — конфиг копируется в `conf-available` и включается через `a2enconf`.
3. `docker-compose.yml` — у MySQL явно заданы `--max-connections=150` (запас втрое к 16 воркерам:
   импортёр, админка, healthcheck) и `--wait-timeout=180 --interactive-timeout=180`,
   чтобы брошенные соединения переставали числиться через три минуты, а не через восемь часов.
4. `docker/import-catalog.php` — CLI-импорт поднимает `wait_timeout` **для своей сессии**:
   он до часа качает картинки, не обращаясь к БД, и общий 180-секундный таймаут его бы убил.

Изменения применяются при следующем деплое (push в `main`).

**Немедленное восстановление на сервере (до деплоя):**

```bash
docker exec noveraile-db mysql -uroot -p"$OPENCART_DB_ROOT_PASSWORD" -e "SHOW STATUS LIKE 'Threads_connected'; SHOW VARIABLES LIKE 'max_connections'; SELECT command, COUNT(*) AS n FROM information_schema.processlist GROUP BY command;"
```

```bash
docker restart noveraile-store
```

Рестарт витрины освобождает все её соединения; базу перезапускать не нужно — это оборвёт
фоновую докачку изображений.

```bash
docker exec noveraile-store tail -50 /var/www/html/system/storage/logs/noveraile-catalog.log
```

**Проверка после деплоя:** под нагрузкой `Threads_connected` не должен превышать ~20.
Если магазину понадобится больше пропускной способности — поднимать `mem_limit` витрины
и `MaxRequestWorkers` **вместе**, сохраняя запас к `max-connections`.

**Возможный следующий шаг (не сделан):** `getPriceBounds()` в
[catalog.php:37-48](opencart/noveraile/catalog/model/catalog.php#L37-L48) считается заново на
каждый рендер каталога и не кешируется — это лишний `MIN/MAX` по всей таблице товаров на
запрос. Кешировать по тому же ключу, что и фасеты. Не включено сюда, чтобы инфраструктурная
правка осталась отдельной и проверяемой.

### B2 — Цвета металла нет в данных вообще (влияет на п.5 и п.6)

В фиде поставщика нет ни одного поля цвета металла — товар описан только
пробой (9K/14K/18K) и качеством камня. Проверено: в `catalog-feed.json` нет ключей
`metal/color/colour`, в `tools/build-catalog-feed.mjs` — тоже.

Следствия:
- фильтр «цвет металла» в коде **уже есть**
  ([catalog.php:172](opencart/noveraile/catalog/controller/page/catalog.php#L172),
  [filters.twig:6](opencart/noveraile/catalog/view/template/page/filters.twig#L6)),
  но скрывается, потому что счётчик по всем трём цветам = 0;
- квиз спрашивает про металл и не может отфильтровать — отсюда «просил розовое, показало белое».

**Без нового источника данных обе правки закрыть невозможно.** Варианты решения — в п.5.4.

### B3 — Часть каталога залита в прод мимо репозитория

В продовой БД лежат товары и атрибуты, созданные внешним инструментом, которого нет в репозитории
(атрибуты с ID `900002…900015` захардкожены в
[catalog.php:434-442](opencart/noveraile/catalog/model/catalog.php#L434-L442) именно поэтому).
Названия у тех товаров — только русские, артикул только в SKU.

**Практическое правило для всех задач ниже:** прежде чем менять что-то, что пишет в каталог,
смотрим что реально лежит в живой базе, а не выводим это из репозитория.
Это прямая причина п.1 и, вероятно, части п.3.

# 1. Названия на языковых версиях (EN показывает русские названия)

### Контекст

Названия товаров и категорий в OpenCart живут в БД (`product_description`, `category_description`)
по одной строке на язык. Модуль тут ни при чём: строки интерфейса (`six_*`) переведены на все
пять языков и лежат в `catalog/language/{en-gb,de-de,cs-cz,ru-ru,uk-ua}/module/noveraile.php`.

Фид **содержит** переводы: у каждой категории и вида изделия имя задано массивом позиционно
по `feed.languages = ["en-gb","de-de","cs-cz","ru-ru","uk-ua"]`, например
`"name":["Rings","Ringe","Prsteny","Кольца","Каблучки"]`.

**Проверено на проде.** На `?language=en-gb` карточки называются «Ожерелье Иллюзия»,
«Кольцо Солитер», «Серьги Минимализм», а SEO-адрес у того же товара английский —
`/en-gb/product/illusion-ring-101-10075-900004`. Категории при этом переведены («Rings»).
То есть английский перевод для товаров существует только в SEO-ключе, а `product_description.name`
для `en-gb` заполнен русским — ровно почерк внешнего импорта (B3, ID категорий `900000+`).

### Диагноз (две независимые причины, чинить обе)

**1.1. Данные.** В продовой БД лежат товары внешнего импорта (B3), у которых имя — только русское
и записано во все языковые строки. Наш импорт их не переписывает: он владеет только своими
артикулами и лишь *отключает* (`status=0`) чужие дубли —
[catalog_feed.php:755-776](opencart/noveraile/admin/model/module/catalog_feed.php#L755-L776).
Если дубль не распознан (артикул отличается регистром/пробелом, или лежит не в `model`/`sku`),
товар остаётся в витрине с русским именем на всех языках.

**1.2. Код — реальный дефект сопоставления языков.** Позиция в массиве имён берётся как индекс
среди **установленных** языков, а не как позиция в `feed.languages`:

```php
// catalog_feed.php:381
$codes = array_keys($languages);          // только установленные языки
// catalog_feed.php:425-427
foreach ($codes as $position => $code) {
    $name = trim($kind['name'][$position] ?? $kind['name'][0]) . ' ' . $product['articul'];
```

Если в магазине установлены не все пять языков (например только `en-gb` и `ru-ru`), то
`position=1` — это русский язык, а `name[1]` — **немецкое** имя. Та же ошибка в
`upsertCategory` ([:257](opencart/noveraile/admin/model/module/catalog_feed.php#L257)),
`productAttributes` ([:515](opencart/noveraile/admin/model/module/catalog_feed.php#L515)),
`describe` ([:583](opencart/noveraile/admin/model/module/catalog_feed.php#L583)),
`metaDescription` ([:626](opencart/noveraile/admin/model/module/catalog_feed.php#L626)).

### Решение

1. Индексировать имена по позиции кода в `feed.languages`, а не по порядку установленных языков.
   Ввести один хелпер `languageIndex(string $code): int` и использовать его везде,
   где сейчас `$position`. Если язык магазина отсутствует в фиде — падать в `en-gb` (индекс 0), явно.
2. Провести аудит живой БД: найти все активные товары, у которых `product_description` совпадает
   для `en-gb` и `ru-ru`, и все, чей артикул есть в фиде, но `product_id` не совпадает с
   `noveraile_feed_product`. Отключить их (не удалять) и/или расширить `retireDuplicates`
   нормализацией артикула (trim + upper + удаление пробелов) с обеих сторон сравнения.
3. Прогнать импорт с `--force`, чтобы переписать описания всех 476 товаров во всех языках.
4. Сбросить кеши `product`, `category`, `noveraile.facet`.

# 3. Убрать точки в заголовках

### Контекст

В шаблонах это уже решено: **все** `<h1>…<h4>` проходят через фильтр `|trim('.')` —
проверено по всем 26 twig-шаблонам расширения. В `CHANGELOG` версии 2.4.0 есть строка
«Removed the trailing full stops from storefront headings in all five languages».
Языковые файлы `en-gb` и `ru-ru` по заголовочным ключам уже чистые.

### Диагноз

Значит, точки, которые видит клиент, приходят **не из шаблонов заголовков**. Остаются три источника:

1. **Контент из БД** — названия товаров/категорий внешнего импорта (см. B3), заголовки статей
   блога, заголовки информационных страниц. `|trim('.')` их подрежет только там, где он есть,
   а, например, `<legend>` в квизе и `.eyebrow`/`.editorial-script` — без фильтра.
2. **Подзаголовки-абзацы**, которые визуально читаются как часть заголовка:
   `six_catalog_intro`, `six_quiz_intro`, `six_no_products`, `six_desired_copy` и т.п. — они
   с точками намеренно.
3. Клиент смотрел версию до выката 2.4.0.

### Решение

1. **Запросить у клиента исходный скриншот к пункту 3** — иначе мы чиним вслепую.
2. Не латать точечно, а зафиксировать правило и покрыть его проверкой:
   заголовочные слоты (`h1–h4`, `legend`, `.eyebrow`, `.editorial-script`, `summary`,
   заголовки карточек, названия кнопок) — без точки в конце; абзацы — с точкой.
3. Прогнать sweep по всем пяти языковым файлам и по контенту БД (названия категорий,
   заголовки статей, `information_description.title`).
4. Добавить тест в `tests/rendered-html.test.mjs`: отрендеренная главная/каталог/карточка
   не содержат `</h1>`, `</h2>`, `</h3>` с точкой перед закрывающим тегом.

### Файлы

- `opencart/noveraile/catalog/view/template/**/*.twig` (добавить `|trim('.')` в `legend`, `.eyebrow`, `summary`)
- `opencart/noveraile/catalog/language/*/module/noveraile.php`
- `tests/rendered-html.test.mjs`

# 4 + 5.3. Выбор фильтра (например «лаб-камни») открывает главную вместо каталога

Это одна и та же поломка, поэтому и чинится одной задачей.

### Контекст

Каталог — собственный роут расширения `extension/noveraile/page/catalog`
([catalog.php](opencart/noveraile/catalog/controller/page/catalog.php)).
На него ведут:
- ссылка «Смотреть лабораторные» на главной:
  `href="{{ six_catalog }}&stone=lab-grown"` — [home.twig:27](opencart/noveraile/catalog/view/template/common/home.twig#L27);
- форма фильтра (GET) с `action="{{ catalog_action }}"` и скрытым полем
  `route=extension/noveraile/page/catalog` — [filters.twig:3-4](opencart/noveraile/catalog/view/template/page/filters.twig#L3-L4).

В OpenCart 4 главная показывается ровно в одном случае: когда параметр `route` в запросе
**потерян или пустой** — фреймворк подставляет `common/home` по умолчанию. То есть симптом
однозначно говорит: до контроллера каталога запрос не доходит, `route` теряется по дороге.

### Статус: **на проде 2026-08-10 не воспроизводится**

Проверено на живом `6moments.store`:

- SEO URL **включены**, и `url->link()` отдаёт гибрид: `https://6moments.store/en-gb?route=extension/noveraile/page/catalog&stone=lab-grown`.
  Query-строка в ссылке есть, поэтому конкатенация `{{ six_catalog }}&stone=…` пока не ломается.
- Кнопка «Shop lab-grown» с главной открывает каталог, фильтр применён
  (`input[name=stone]:checked == lab-grown`), выдача 429 позиций — ровно счётчик LAB.
- `?type=rings` даёт 217 позиций — ровно счётчик колец в фиде.

Значит одно из трёх: правку уже выкатили после того, как клиент писал документ; клиент смотрел
другой домен (`katya-dev.duckdns.org` в момент проверки лежал целиком, см. B1); либо это был
эпизод во время того же исчерпания соединений.

**Что от этого остаётся в работе:** страховка. Конструкция `{{ six_catalog }}&параметр` держится
только на том, что SEO-адрес сейчас сохраняет `?route=`. Стоит поменять формат SEO-адресов или
дать роуту каталога собственный keyword — и все такие ссылки станут битыми молча. Поэтому
пункты 1–4 «Решения» ниже делаем как профилактику, а не как починку.

**Перед началом работ запросить у клиента точную ссылку и скриншот** — если баг остался,
он воспроизводится каким-то конкретным путём, и без него мы правим вслепую.

### Решение (делать вне зависимости от того, какая гипотеза подтвердится)

1. **Убрать конкатенацию URL из шаблонов.** Все ссылки с параметрами строить в контроллере
   через `$this->url->link('extension/noveraile/page/catalog', $lang . '&stone=lab-grown')`,
   а в twig подставлять готовую переменную. `{{ six_catalog }}&stone=…` — антипаттерн,
   он ломается при любом виде rewrite.
2. **Дать роуту каталога SEO-keyword** (`oc_seo_url`, `key='route'`), чтобы он корректно работал
   и с включёнными, и с выключенными SEO URL.
3. **Форму фильтра перевести на POST→redirect или на явный `index.php` в action**, чтобы GET-сабмит
   никогда не терял `route`. Минимальный вариант: `action="index.php"` + скрытые `route`/`language`.
4. Добавить smoke-тест: запрос каталога с каждым фильтром возвращает страницу каталога (200 + маркер
   `data-six-filters`), а не главную.

### Критерии приёмки

- «Смотреть лабораторные» с главной открывает каталог с активным фильтром `stone=lab-grown`.
- Каждый фильтр (металл, проба, качество, огранка, размер, цена, наличие, доставка) даёт
  отфильтрованную выдачу и корректный счётчик.
- Работает и при включённых, и при выключенных SEO URL.

# 5.1. Убрать 375 пробу

### Контекст

375 проба — это 9K, ключ `CT_9` в фиде. Она входит в опцию «Gold & diamond quality»
(значения `9K · LAB`, `9K · G/SI`, …) и в фасет «Проба» фильтра
([catalog.php:112-113, 173](opencart/noveraile/catalog/controller/page/catalog.php#L112-L113)).

### Диагноз и **важное бизнес-последствие**

Посчитано по фиду: **все 476 товаров** доступны в 9K, 14K и 18K. Цена товара в OpenCart —
это минимальная комбинация, а минимум почти всегда даёт именно 9K.

> Если убрать 375 пробу, цена «от» вырастет в среднем на **30.2 %**, максимум на **40.6 %**.

Это не техническое, а коммерческое решение. Нужно подтверждение клиента.

**Вариант A — «спрятать» (быстро, 30 мин, обратимо).**

Половинчатый: клиент увидит 9K в выпадающем списке на карточке.

**Вариант B — «убрать из продажи» (правильно, 2 ч).**
Исключить `CT_9` при сборке фида (`tools/build-catalog-feed.mjs`) и при импорте:
опция пересобирается без 9K, база цен пересчитывается по минимуму из 14K/18K,

- B: `tools/build-catalog-feed.mjs`, `opencart/noveraile/admin/model/module/catalog_feed.php`

### Критерии приёмки

# 5.2. Качество камня — привести к образцу, лишнее убрать

### Контекст

Фасет «качество камня» собирается из двух источников и склеивается в
[catalog.php:104-119](opencart/noveraile/catalog/model/catalog.php#L104-L119):

1. атрибут `stone_quality` (в проде это ID `900013` из внешнего импорта, B3);
2. значения опции, распознанные регулярным выражением
   `/\b(?:[D-J]\/(?:FL|IF|VVS[12]?|VS[12]?|SI[12]?|I[123]?)|LAB)\b/i`
   ([catalog.php:169](opencart/noveraile/catalog/model/catalog.php#L169)).

Наш импорт **не пишет** атрибут `stone_quality` вовсе, поэтому канонический список из фида —
ровно пять значений: `LAB, G/SI, G/VS2, F/VS2, D/VVS2`.

### Диагноз — причина найдена точно (снято с живого сайта)

Сейчас фильтр показывает **восемь** пунктов вместо пяти:

```
D/VVS2 (462)
F/VS2 (462)
F/VS2; D/VVS2; G/SI (3)                 ← лишнее
F/VS2; D/VVS2; G/SI; G/VS2 (10)         ← лишнее
F/VS2; D/VVS2; G/SI; G/VS2; LAB (121)   ← лишнее
G/SI (476)
G/VS2 (456)
LAB (429)
```

Три «склейки» — это значения атрибута `stone_quality` внешнего импорта. На карточке товара
видно исходник: `Diamond quality: F/VS2; D/VVS2; G/SI; G/VS2; LAB` — **несколько значений через
точку с запятой в одном поле**.

Атрибут числится многозначным
([catalog.php:60](opencart/noveraile/catalog/model/catalog.php#L60)), но `expandFacet()` разбивает
текст **только по запятой**:

```php
// catalog.php:193
foreach (explode(',', (string)$row['value']) as $value) {
```

Точка с запятой не разбирается, поэтому вся строка целиком становится «значением качества»
и попадает в фильтр отдельным пунктом. Тот же формат и у пробы
(`375 / 9K; 585 / 14K; 750 / 18K`), и у коллекций — то есть баг общий для всех многозначных
атрибутов, просто в фильтре качества он заметен.

### Решение

1. Разбивать многозначные атрибуты по `,` **и** по `;` (`preg_split('/\s*[;,]\s*/u', …)`) —
   это чинит корень и убирает склейки во всех фасетах сразу.
2. Дополнительно закрыть фасет качества белым списком из фида — `D/VVS2, F/VS2, G/VS2, G/SI, LAB` —
   чтобы никакой будущий импорт не мог протащить в фильтр произвольный текст.

   `D/VVS2 → F/VS2 → G/VS2 → G/SI → LAB`.
4. Поднять версию ключа кеша фасетов `noveraile.facet.v3.*` → `v4`, иначе старые значения
   останутся в кеше.

# 5.4. Фильтр по цвету металла (белое / жёлтое / розовое золото)

### Контекст

Код фильтра **уже написан** и работает: белый список
`['white-gold','yellow-gold','rose-gold']`, локализованные подписи для всех пяти языков
([catalog.php:482-487](opencart/noveraile/catalog/model/catalog.php#L482-L487)),
свотчи в разметке ([filters.twig:6](opencart/noveraile/catalog/view/template/page/filters.twig#L6)),
предикат по атрибуту `metal` + по имени опции
([catalog.php:351-371](opencart/noveraile/catalog/model/catalog.php#L351-L371)).

### Диагноз

Данных нет (B2). `attributeMap()` не содержит ключа `metal` вовсе, поэтому предикат падает на
поиск по тегу `white-gold`, которого нет ни у одного товара → счётчик 0 → секция скрывается
([catalog.php:176-183](opencart/noveraile/catalog/controller/page/catalog.php#L176-L183)).
Это не баг отображения — это отсутствующее измерение каталога.

### Решение — три варианта, по возрастанию стоимости

**Вариант 1. Цвет как ещё одна опция товара (правильный, 12–16 ч).**
У ювелирки цвет металла — это выбор покупателя, а не свойство артикула: один и тот же артикул
делают в белом, жёлтом и розовом. Тогда:
- расширяем фид полем `metals: ["white","yellow","rose"]` на товар (нужен ответ поставщика,
  есть ли надбавка за родирование белого золота);
- импорт заводит третью опцию-select «Цвет металла» и атрибут `metal` для фильтрации;
- фильтр и квиз начинают работать без единой правки в их коде;
- заказ уезжает с выбранным цветом.

**Вариант 2. Цвет как атрибут товара (быстрый, 6–8 ч).**
Если поставщик подтвердит, что артикул выпускается в одном конкретном цвете — добавляем колонку
в CSV, поле в фид, атрибут `metal` в импорт. Фильтр заработает сразу.

**Вариант 3. Заглушка (не рекомендуется).**
Проставить цвет вручную в админке для части ассортимента. Развалится при следующем импорте
(`--force` перезапишет атрибуты).

**Рекомендация:** уточнить у поставщика, вариативен ли цвет по артикулу. Если да — вариант 1,
если нет — вариант 2. Оба требуют нового столбца в экспорте поставщика — **это внешняя зависимость,
её надо запрашивать сегодня**, иначе пункты 5.4 и 6 встанут.

# 6. Квиз выдаёт нерелевантный цвет металла

### Контекст

Квиз — статический список карточек, отфильтрованный на клиенте:
- контроллер [quiz.php](opencart/noveraile/catalog/controller/page/quiz.php) кладёт в карточку
  `data-tags` и `data-price`;
- ранжирование — [noveraile.js:841-866](opencart/noveraile/catalog/view/javascript/noveraile.js#L841-L866).

### Проверено на живом сайте: сломан не только металл

На странице квиза 48 карточек. Их `data-tags` выглядят так:

```
necklace,illusion-necklace,round,delivery-10,preorder,carat-0.12,central-carat-0.06,
stones-25,not-certified,diamond,375,585,750,quality-f-vs2,…,natural,lab-grown,collection-iluzja
```

- **Ни у одной из 48 карточек нет тега цвета металла** — подтверждает диагноз ниже.
- **Ни у одной нет тега момента** (`engagement`, `wedding`, `motherhood`, `career`,
  `self-purchase`, `milestone`). Живые теги пришли от внешнего импорта (B3) и не совпадают с тем,
  что кладёт наш `tags()`.

А момент — это **самый весомый критерий** ранжирования
([noveraile.js:849](opencart/noveraile/catalog/view/javascript/noveraile.js#L849), вес 16 из 31).
То есть из пяти вопросов квиза реально работают только три:

| Вопрос | Совпадение | Почему |
|---|---|---|
| Что вы отмечаете | **не работает** | тега момента нет ни у одного товара |
| Бюджет | работает | цена в `data-price` |
| Тип украшения | работает | теги `ring` / `earrings` / `necklace` / `bracelet` есть |
| Металл | **не работает** | тега цвета нет ни у одного товара (B2) |
| Камень | работает | теги `natural` / `lab-grown` есть |

Клиент заметил металл, но по факту главный вопрос квиза тоже ни на что не влияет.
Чинится это тем же действием: привести теги товаров к тому, что ожидает квиз, — то есть
прогнать импорт из фида (он кладёт и момент, и, после п.5.4, цвет металла), а не подпирать
JS-фильтр.

### Диагноз (подтверждён по коду, две причины)

**6.1.** Металл проверяется как `metal = !values.metal || tags.includes(values.metal)`.
Теги товара формируются импортом в
[catalog_feed.php:560-579](opencart/noveraile/admin/model/module/catalog_feed.php#L560-L579)
и содержат тип, момент, срок доставки, стиль, огранку, коллекцию, происхождение камня и пробу —
**цвета металла среди них нет**. Значит `metal` всегда `false`, товар никогда не «exact»,
и срабатывает добор «дополним до четырёх по общему счёту» — в него попадают товары с любым цветом.
Отсюда «просил розовое, показало белое».

**6.2.** Есть мёртвый код, который должен был это компенсировать:

```php
// quiz.php:9-10
$starter_tags = ['RI'=>'ring,yellow-gold','WE'=>'ring,rose-gold', ...];
$parts = explode('-', (string)$product['model']);
$tags  = trim($product['tag'] . ',' . ($starter_tags[$parts[1] ?? ''] ?? ''), ',');
```

Он рассчитан на модели демо-каталога вида `NVR-RI-001`. У реальных товаров `model` — это артикул
(`101-10010(2.3)`), поэтому `$parts[1]` никогда не совпадёт с ключами. Даже если бы совпал —
он бы присваивал цвет по типу изделия, что заведомо неверно.

### Решение

1. Снести `$starter_tags` целиком — это источник ложных данных.
2. После п.5.4 добавить цвет металла в теги товара (`tags()` в импорте) — квиз заработает без
   правок JS.
3. Пока данных нет — **честное поведение вместо угадывания**: если по цвету совпадений нет,
   не подмешивать чужой цвет в добор, а показать сообщение «по этому цвету пока нет подходящих
   изделий, вот близкие варианты» и явно пометить их. Сейчас интерфейс молча врёт.
4. Заодно: в доборе `ranked.filter(item => !selected.includes(item))` — сравнение по ссылке на
   объект-обёртку, работает, но хрупко; переписать на `Set` по индексу.

### Файлы

- `opencart/noveraile/catalog/controller/page/quiz.php:9-10`
- `opencart/noveraile/catalog/view/javascript/noveraile.js:841-866`
- `opencart/noveraile/admin/model/module/catalog_feed.php` (`tags()`)

### Критерии приёмки

- Выбор «розовое золото» в квизе → в выдаче только розовое золото.
- Если совпадений нет — явное сообщение, а не молчаливая подмена.

### Промпт для Codex

```
Квиз 6 Moments выдаёт товары не того цвета металла, который выбрал пользователь.
На живом сайте ни у одной из 48 карточек квиза нет ни тега цвета металла, ни тега момента
```

# 7. Размер кольца: выбор в карточке, отображение в корзине и в заказе

### Контекст

Механика **уже реализована**:
- опция «Ring size» создаётся импортом со значениями EU `50,52,54,56,58,60`
  ([catalog_feed.php:358-377](opencart/noveraile/admin/model/module/catalog_feed.php#L358-L377));

- карточка рендерит любые select-опции ([product.twig:61-70](opencart/noveraile/catalog/view/template/product/product.twig#L61-L70));
- корзина показывает выбранные опции ([cart_list.twig:21-27](opencart/noveraile/catalog/view/template/checkout/cart_list.twig#L21-L27));
- в заказ опции попадают штатным механизмом OpenCart (`oc_order_option`) — видны в админке и в письме.

**Проверено на проде:** на карточке кольца
[`/en-gb/product/illusion-ring-101-10075-900004`](https://6moments.store/en-gb/product/illusion-ring-101-10075-900004)
ровно **одна** группа опций — «Gold / diamond quality». Опции размера нет вообще.
Значит сломалась одна из четырёх конкретных вещей ниже.

### Диагноз — что проверять по порядку

1. **Опция существует, но пустая.** `installRingSizeOption()` возвращает сохранённый
   `module_noveraile_ring_size_option_id` **без проверки, что у опции есть значения**
   ([catalog_feed.php:359-361](opencart/noveraile/admin/model/module/catalog_feed.php#L359-L361)).
   Если такая опция когда-то была создана пустой, `ringSizeValues()` вернёт `[]`, и блок
   `if ($size_values)` молча не добавит опцию к товару. **Самый вероятный сценарий и явный дефект.**
2. **Товары не переписаны.** Импорт пропускает товар, если контрольная сумма совпала
   ([:80](opencart/noveraile/admin/model/module/catalog_feed.php#L80)). Если размер добавили после
   первой заливки — нужен `--force`.
3. **Товары в витрине не из фида** (B3): у внешнего импорта опции размера нет вовсе.
4. Категория товара в фиде не `RING` (для колец в фиде это всегда `RING`, проверено).

### Решение

1. Убрать «тихий» путь: если у опции размера нет значений — **пересоздавать их**, а не молча
   пропускать. Если опция размера не добавилась к кольцу — импорт должен падать с внятной
   ошибкой, как он уже делает для опции золота/качества
   ([:404](opencart/noveraile/admin/model/module/catalog_feed.php#L404)).
2. Прогнать `noveraile-import-catalog --force --no-images` и проверить кольцо в витрине.
3. **Размерная сетка — решение клиента.** Клиент пишет «человек выбирает кольцо 17 размера»:
   это российская сетка (внутренний диаметр в мм), а в магазине сейчас EU-окружность

   - показывать двойную подпись `17 (RU) · 53 (EU)` — рекомендуется, работает для всех рынков;
   - переключать сетку по языку витрины;

   с шагом 0.5–1. Нужно подтвердить у поставщика доступный диапазон и шаг.
4. Проверить сквозной путь: карточка → корзина → письмо → админка заказа.

# 8. Страница оформления заказа: настроить доставку и оплату

### Контекст

В расширении есть три метода:

| Метод | Файлы | Статус по умолчанию |
|---|---|---|
| Stripe Checkout | `catalog/controller/payment/stripe.php`, `catalog/model/payment/stripe.php` | выключен |
| DHL Express | `catalog/model/shipping/dhl.php` (EU / остальной мир) | включается автоматически |
| DPD | `catalog/model/shipping/dpd.php` (Украина / EU) | включается автоматически |

Логика включения: Stripe включается сам **только если заданы оба секрета** `STRIPE_SECRET_KEY`
и `STRIPE_WEBHOOK_SECRET` ([noveraile.php:226-231](opencart/noveraile/admin/model/module/noveraile.php#L226-L231));
DHL и DPD включаются на каждом деплое, если магазин управляемый
([noveraile.php:266-272](opencart/noveraile/admin/model/module/noveraile.php#L266-L272)).

### Диагноз — найден конкретный дефект в обеих моделях доставки

```php
// dhl.php:28 и dpd.php:28
'text' => $this->currency->format($this->tax->calculate($tier['cost'], $tax_class_id, ...))
```

Переменная `$tier` **нигде не определена**. В PHP 8 это warning + `null`, то есть покупателю
в списке способов доставки показывается **«0.00»**, хотя в заказ уходит корректная стоимость
из `$cost`. Это ровно тот случай, когда «доставка не настроена» с точки зрения клиента.
Должно быть `$cost`.

Кроме кода, для рабочего чекаута нужна конфигурация, которой в репозитории быть не может:

- ключи Stripe (`sk_live_…`, `whsec_…`) и регистрация вебхука
  `https://<домен>/index.php?route=extension/noveraile/payment/stripe.webhook`;
- гео-зоны OpenCart для DHL/DPD (сейчас `*_geo_zone_id = 0` — «все зоны»);
- налоговые классы и `config_tax`;
- страница «Условия» для чекаута (`config_checkout_id`), гостевой чекаут;
- валюты и способ округления;
- проверка `config_stock_checkout = 1` (импорт его выставляет — товары делаются под заказ).

### Решение

1. **Починить `$tier` → `$cost`** в обеих моделях (5 минут, но именно это ломает витрину).
2. Собрать у клиента: Stripe-ключи (test + live), юрлицо/адрес для чеков, реальные тарифы
   и сроки доставки по зонам, страны, куда доставляем.
3. Настроить гео-зоны и тарифы в админке модуля, а не в коде.

# 9. Логотип: убрать «солнышко» вокруг цифры 6

### Контекст

Логотип — векторный: [opencart/noveraile/image/catalog/noveraile/logo-6-moments.svg](opencart/noveraile/image/catalog/noveraile/logo-6-moments.svg),

### Диагноз

«Солнышко» — это восемь лучей, одна строка в SVG:

```xml
<g fill="none" stroke="#b08a55" stroke-width="1.4">
  <circle cx="39" cy="46" r="27"/>                                   <!-- кольцо, оставляем -->
  <path d="M39 12v8M39 72v8M5 46h8M65 46h8M15 22l6 6M57 64l6 6M63 22l-6 6M21 64l-6 6"/>  <!-- лучи, удаляем -->
</g>
```

### Решение

Удалить строку с лучами. Кольцо вокруг шестёрки оставить — оно читается как ювелирное кольцо
и держит композицию. Файл в репозитории; поскольку картинки лежат в Docker volume, нужно
убедиться, что деплой обновляет версионируемые изображения (README это подтверждает).
Логотип используется также в `og-store.png` и `favicon.svg` — их нужно проверить и при
необходимости перерисовать, иначе в шаринге и во вкладке останется старый знак.

### Критерии приёмки

- В хедере, футере и на мобильной версии — логотип без лучей.
- Favicon и og-изображение согласованы с новым знаком.

# 10. Хедер: WhatsApp вместо телефона, сердечко вишлиста крупнее

### Контекст

[header.twig:57-58](opencart/noveraile/catalog/view/template/common/header.twig#L57-L58):

```twig
{% if six_phone %}<a href="tel:{{ six_phone_href }}">{{ six_phone }}</a>{% endif %}
<a href="{{ wishlist }}" aria-label="{{ six_wishlist }}">♡</a>
```

Ссылка на WhatsApp уже приходит в шаблон: `six_contact_url`
([theme.php:54](opencart/noveraile/catalog/controller/event/theme.php#L54)),
значение настраивается в админке (`module_noveraile_whatsapp`, по умолчанию `https://wa.me/491707647729`).
Телефон — та же секция, ниже он ещё раз повторяется в мобильном меню
([header.twig:78](opencart/noveraile/catalog/view/template/common/header.twig#L78)).

Сердечко — текстовый символ `♡`, наследует `font-size: 10px` от правила
[noveraile.css:356](opencart/noveraile/catalog/view/stylesheet/noveraile.css#L356) для `.header-actions a`,
поэтому и выглядит мелким.

### Решение

1. Заменить телефонную ссылку на кнопку WhatsApp: иконка + подпись, `href="{{ six_contact_url }}"`,
   `target="_blank" rel="noopener"`, доступное имя. То же в мобильном меню — там телефон дублируется.
2. Сердечко: заменить текстовый символ на тот же SVG, что уже используется на карточке товара
   ([product.twig:77](opencart/noveraile/catalog/view/template/product/product.twig#L77)), и задать ему
   явный размер (`width/height: 20px`) отдельным правилом — а не менять `font-size` у всех
   ссылок хедера. Тогда иконки в хедере (сумка 17px, сердце 20px) будут единой системы.
3. Не терять телефон совсем: перенести его в футер/на страницу контактов, чтобы не потерять
   канал для тех, кто не пользуется WhatsApp.

### Критерии приёмки

- В хедере кнопка WhatsApp открывает чат в новой вкладке; номер телефона в хедере отсутствует.
- Сердечко визуально сопоставимо с иконкой сумки, кликабельная область ≥ 44×44 px на мобильном.
- Ничего не разъехалось на 980px и 680px.

### Промпт для Codex

```
Правки хедера 6 Moments в opencart/noveraile/catalog/view/template/common/header.twig:
1) Строка 57: замени телефонную ссылку <a href="tel:…"> на кнопку WhatsApp.
   URL уже есть в переменной six_contact_url. Сделай <a class="header-whatsapp"
   href="{{ six_contact_url }}" target="_blank" rel="noopener" aria-label="WhatsApp"> с inline-SVG

   используется в product.twig (класс wishlist-icon), и добавь в
```
